the checks, and time / memory estimates. **Nothing here is used by the running trainer**: the live yaml, the live code tree and the live prompt directory were not touched;

(reward CPU cost), `scripts/probe_microbatch_memory.py` (GPU memory probe, NOT run), `tests/test_b2048_bin.py` (14 tests).

## 2. The prompt data

**Layout.** The trainer's loader (`load_rl_prompts` -> `iter_rows`) reads every parquet under the directory, files sorted by full path, and the schedule indexes the rows
globally. `rl_prompts_v3` therefore holds the 77 per-language files of `rl_prompts_v2` as **hard links** (same inodes, no copy, v2 untouched: directory mtime unchanged) and the
new rows in a subdirectory `zz_b2048/` (sorts after `zul.parquet`). Every old row keeps its global index: the first 5,940,000 rows of the v3 table are byte-identical to v2
(checked on the loaded tables); v3 has 5,986,200 rows. The new files have the v2 columns (`english, iso, language, src_afr_tokens, length_bin, n_sentences, source_dataset,
licence`) + `doc_id`, `window_id`. They are also valid `--windows` input for `rlhf/scripts/build_rl_bin_v2.py` (same `<iso>.parquet` convention).

**Rows.** 600 b2048 rows for each of the 77 languages = 46,200 (450 fineweb-edu `odc-by` + 150 wikipedia `share_alike` per language, the 75/25 mix of the old bins). The
stage draws ~6,260 prompts (298 steps x 21), uniformly over languages with weight 2.5 on the 17 weakest + efi: 43..175 per language (weighted 152 on average, others 60),
so nothing repeats inside a language. Old bins unchanged (per language and bin: 30,000 for the 19 oldest languages, 90,000 for 8 boosted ones, 150,000 pcm, 5,000 for the 57
added ones - identical in v2 and v3).

**Sources and windows.** English only: fineweb-edu `sample/10BT/003_00000.parquet` (first 50,048 documents of >= 3,600 characters -> 17,004 windows) and wikimedia/wikipedia
`20231101.en/train-00012-of-00041.parquet` (first 18,752 long documents -> 5,609 windows); 2.4 GB downloaded to a scratch cache, no Hub / S3 writes. A window is a run of
contiguous whole sentences of one document (`segments.split_sentences`, which reproduces the v2 `n_sentences` in 99.99 % of the old windows), joined by single spaces, no newline,
NFC; budget drawn uniformly in 1,025..2,048, at most 2 non-overlapping windows per document, sentences with web artifacts act as barriers; lines that are not complete
sentences (headings, menus, list items) are dropped first. `src_afr_tokens` = `len(Tokenizer.from_file(afro-xlmr-large-76L tokenizer.json).encode(text).ids)` with special
tokens - verified equal to the v2 column on 300 sampled old windows (100 %), and recomputed on every window before it is accepted.

| `src_afr_tokens` | min | p25 | p50 | p75 | max | mean |
|---|---|---|---|---|---|---|
| b2048 pool (21,981 windows) | 1,025 | 1,083 | 1,179 | 1,365 | 2,048 | 1,259 |

Sentences per window: mean 44, p50 42, p90 60, p99 83, max 183 (0.2 % above 100). Gemma prompt tokens (chat frame + tags, all 46,200 rows, real tokenizer): min 802, p50 1,073,
p90 1,454, p99 1,796, **max 2,153**.

**Filters - the original builder is not available.** `gemma_rl_windows.py` / `gemma_rl_assemble.py` (old box) are neither on the rental nor in the repo, so the
`stats.json` filters were re-derived from the 1.4 M kept windows of v2 (58k sampled): a rule is adopted when 100 % of the kept windows pass it and its distribution has a cliff at
the threshold ("envelope" method). Four rules are exact in that sense, three are approximations:

| rule (stats.json name) | implementation | evidence in the old kept windows |
|---|---|---|
| repetition | no 4-gram of lower-cased `[a-z']+` words seen >= 3 times | max count exactly 2 in 29k b512/b1024 windows (every other tokenisation gave 3..66) |
| numeric_or_math | digits / characters <= 0.06 (+ >= 20 math symbols or LaTeX commands) | p99.99 0.0597, max 0.0600 |
| technical_vocabulary | share of `[A-Za-z]+` words with >= 13 letters <= 0.03 | max 0.0287 / 0.0300 / 0.0299 / 0.0294 in b1024 / b256 / b512 / b64 |
| hard_to_read | Flesch reading ease >= 30, syllables = vowel groups `[aeiouy]+`, sentences = non-empty splits on `[.!?]+` | min 29.8, p0.1 30.1 (silent-e or `split_sentences` variants had a 0.3-3 % tail below 30) |
| artifact | URLs, e-mail, (c), control characters, `[12]` / `[citation`, templates, HTML; >= 2 boilerplate phrases; >= 8 verse numbers; >= 6 menu glyphs | approximation (old windows still contain a few) |
| shouting_or_acronyms | > 15 % ALL-CAPS words of >= 3 letters | no cliff (max 0.11-0.14); 0.15 % of the windows |

Recall on 30,000 old kept windows: b64 99.88 %, b256 99.97 %, b512 99.53 %, b1024 99.37 % (rejections: artifact 0.6 %, hard_to_read 0.1 %). Attempts on fineweb-edu (4 tries
per document): 88,436 windows built, 17,004 kept (19 %): repetition 35,685, Flesch 27,820, artifact 3,665, technical 3,166, numeric 1,071, shouting 25. Longer windows are stricter
by construction (a repeated 4-gram anywhere in 2,048 tokens), as the SabiYarn b2048 note found (repetition removed 51 % there).

**Duplicates.** Sentence hashes (>= 25 characters) of all b1024 and b512 windows of v2 (13.5 M distinct, cheap regex splitter on both sides): 630 of 22,611 candidate windows had
> 10 % of their sentences in an existing window and were dropped (2,438 share any sentence - mostly boilerplate). Two windows were dropped because their hold-out hash is
below 3e-5 (keeps the trainer's 128-prompt hash hold-out exactly the set it is now). Result: 21,981 distinct windows (16,414 fineweb-edu + 5,567 wikipedia) from 20,735 documents.
Windows are reused across languages (2.1 uses on average; the old bins: ~3.9), never twice inside a language. The 46,200 rows contain no row-level duplicates; the b2048 stage
draws 6,258 prompts of which 5,328 have distinct English (the rest is the same window in another language).

## 4. The staged config

`gemma_mt_2c/configs/rl_rtxpro_phase2c_b2048.yaml` = the live yaml with only these edits (unified diff of the non-comment lines; `diff -u` of the files also shows the 2-line header
comment and the trailing comments; `reward:`, `language_weights` (incl. `efi: 2.5`), `calibration_path`, `hub_repo_id`, `kl_guard_*`, `archive_*`, `micro_batch_tokens` are
byte-identical):

```diff
-prompts_path: /workspace/sft_build/gemma/rl_prompts_v2
+prompts_path: /workspace/sft_build/gemma/rl_prompts_v3
-steps: 1135
+steps: 1433
-vllm_max_model_len: 8192
+vllm_max_model_len: 10240
-max_src_tokens: 1024
+max_src_tokens: 2048
   b1024: 149
+  b2048: 298                 # curriculum_steps, after b1024
   b1024: 42
+  b2048: 21                  # prompts_per_step_by_bin
   b1024: 3584
-  mixed: 3584
+  b2048: 7168                # max_new_tokens_by_bin
+  mixed: 7168
+eval_min_per_bin: 16
```

Why each line:

* **`curriculum_steps.b2048: 298`, `prompts_per_step_by_bin.b2048: 21`**: 21 x 16 = 336 completions per step; round(100,000 / 336) = 298 steps = 100,128 completions (the mixed stage keeps its 149
  steps -> `steps` 1433). **150k would be 446 steps** (149,856 completions; `steps` 1581, +148 steps, ~+8.4 h). 21 prompts is also the KV sweet spot (section 7): 336 sequences
  x ~2.5k completion tokens ~ 840k tokens against 996k of vLLM KV cache.
* **`max_new_tokens_by_bin.b2048: 7168`** (3.5 x 2,048, the b1024 ratio 3584/1024). Evidence: completion length / English source length in Gemma tokens, from the human references of
  the 41 languages that have human references (`flores_dev_all_v2.jsonl`, corpus level; the other 36 have none; most expanding: kbp 3.22, nus 2.90, yor 2.70, fon 2.56, kik 2.54,
  tir 2.47, tum 2.27; median language 1.97, 90th percentile 2.54); the longest b2048 prompt is 2,153 Gemma tokens, so the worst language on the worst window needs ~6.9k - **10 % headroom** (b1024: 22 %, where 0.67 % of the completions
  were unfinished at its cap, finished rate 0.9933 in phase 2). The b2048 stage has the same kind of tail: unfinished completions are the -2 `no_end_of_turn` failure. 8192 would
  buy headroom for kbp / nus on the longest windows at +12 s per step when a runaway sample exists (decode is ~10 ms per token and a step ends with its longest completion).
* **`mixed: 3584 -> 7168`** is not optional: the trainer uses ONE `max_new_tokens` per step (`max_new_tokens_by_bin[mixed]`); with 3584 every b2048 prompt of the mixture would be truncated
  (-2). Cost: a runaway sample of a short prompt may now decode 7,168 tokens; the step already waits for its b2048 completions.
* **`vllm_max_model_len: 10240`**: longest prompt 2,153 + 7,168 = 9,321 (the engine raises `SamplerError` for any request above the limit, which would crash-loop the supervisor);
  `validate_config` also needs >= max cap + 512.
* **`max_src_tokens: 2048`**: `load_rl_prompts` drops rows above it (`source_too_long`); with 1024 **all 46,200 b2048 rows are dropped and the stage vanishes from the schedule without a
  message** (the old `PromptSchedule` skips curriculum bins without prompts). The patched `train_rl` now refuses to start in that situation.
* **`eval_min_per_bin: 16`** (new key, needs the patched `train_rl.py`; a live-code trainer rejects the unknown key): without it the 128-prompt hash hold-out gets ~0.6 b2048 prompts
  (the bin is 0.8 % of the rows) and `eval/reward_bin/b2048` would be empty. Cost: every evaluation (every 25 steps, from the first restart on) decodes 16 b2048 prompts: ~+75 s (the
  longest greedy completion), ~38 evaluations -> ~0.8 h.

Not changed on purpose: `micro_batch_tokens`/`micro_batch_seqs` (the supervisor ladder overrides them anyway), `vllm_gpu_memory_utilization` 0.20, `vllm_max_num_seqs` 512 (336 < 512),
learning rate 2e-6 (a b2048 step has half the samples of a b1024 step: noisier gradient, same lr, KL guard on), `kl_guard`, `reward`.

## 5. Code changes (small; `gemma_mt_2c_b2048_overlay/` - copy into the live tree at the restart)

1. `gemma_mt/rl/train_rl.py`: `RLConfig.eval_min_per_bin` (default 0 = old behaviour) and `split_eval_prompts(..., min_per_bin)`; the plain `n_eval` hash selection is never changed, thin
   bins are topped up with their smallest-hash prompts and every other copy of the same English; a `ValueError` when a `curriculum_steps` bin has no prompts; `validate_config` check.
2. `gemma_mt/rl/segments.py` (**optional, behaviour-identical performance fix**): `_is_boundary` ran `_LAST_WORD.search(head)` over the whole text before every candidate full stop
   (quadratic). It now searches the last 256 characters (a longer "word" is no abbreviation / initial / list number). Test: 400 random texts incl. 255/257-character words, old vs
   new splitter identical. Effect on the reward CPU (stub scorer, 16 samples per prompt, loaded rental, same synthetic inputs before / after): b1024-sized step (672 samples) 61.8 s -> 41.5 s;
   b2048 step (336 samples of 48 sentences, 98 % of the outputs with a different sentence count) 98.0 s -> 51.2 s; on real b2048 windows 40.2 s. The b2048 step then costs 1.0-1.25x a
   b1024 step instead of 1.6x; without the fix the stage would lose ~15 s per step (~1.2 h) to sentence splitting.
3. New: `scripts/build_rl_prompts_b2048.py`, `verify_b2048_prompts.py`, `bench_reward_b2048.py`, `probe_microbatch_memory.py`, `tests/test_b2048_bin.py`.

## 7. Time and memory estimate

**Measured per step (runs/rl2c and runs/rl2 metrics.jsonl):** b256 31.5 s (768 completions), b512 62 s quiet / 72.5 s average (672), phase-2 b1024 136 s (672, group 8) -> ~140 s at
group 16. `t_gen` ~ 10 ms x the longest completion in the batch (b64 3.8 s / 384 tokens, b256 9.8 s / 1,280, b512 23.5 s / 2,304, b1024 37.1 s / 3,584): generation is tail-bound.
The update costs 40 + 11 x (mean sequence length in k tokens) microseconds per token (42 / 46 / 59 us at b256 / b512 / b1024).

| stage | completions per step | est. seconds per step (quiet host) | s / completion | steps | hours |
|---|---|---|---|---|---|
| b2048, 100k completions (298 steps) | 336 | **~200 (170-250)**: generation ~75 (7,168 x ~10.5 ms), reward ~40 (QE ~12 + CPU ~28), update ~85 (1.14 M tokens x 75 us), sync ~3 | ~0.6 (b1024 0.21) | 298 | **~17 (14.5-21)** |
| b2048, 150k completions (446 steps) | 336 | same | same | 446 | **~25 (21-31)** |
| mixed, 5 bins (was 4) | 672 | ~165 (140-200): generation ~70 (cap 7168 reached by a runaway or a b2048 sample), reward ~27 (12.4k chunks), update ~65-80 (mean sequence 1.3k tokens, 672 sequences in micro-batches of 2) | 0.25 | 149 | ~6.8 (5.8-8.3), was ~3.1-4.3 (~75-105 s per step) |

The added wall time is ~+20 h for 100k (+28 h for 150k) on top of the ~15-19 h left of the old plan. The host is currently **CPU-starved**: the container has a cgroup quota of 30.7
CPUs (`/sys/fs/cgroup/cpu.max` 3072000/100000, `nr_throttled` 759k of 3.9 M periods) and a data-generation job (`gen_31b.py`, ~24 processes) uses most of it. Since ~07:15 the 2c steps
take 105-136 s instead of 62 s (generation 40-60 s instead of 20 s, consensus 6-10 s instead of 3). Everything above scales by +30-80 % while that job runs. The builder of this
task ran with 3 workers at nice 19 (a first attempt with 40 workers at 07:50-07:58 coincided with steps of 155-198 s; killed and throttled - this task's only visible side effect).
A cheaper b2048 stage is not available through larger steps: cost is linear in tokens (~0.6 s per completion), and 28+ prompts per step would exceed the KV cache.

**vLLM.** KV bytes per token = 18 layers x 2 x 1 KV head x 256 dim x 2 B = 18,432 B; the live engine reports `GPU KV cache size: 994,607 tokens` (17.1 GiB at `vllm_gpu_memory_utilization`
0.20). A b2048 step: prompts are prefix-cached (21 x ~1.1k tokens) + 336 completions of ~2.3-3.1k tokens (bench: 3.1k) ~ 0.8-1.1 M tokens at the peak -> at the limit of the cache; sequences beyond are
queued / preempted (recomputed), which lengthens generation but cannot fail. One 9.3k-token sequence = 172 MB. `max_model_len` 10240 only changes the per-request limit
(the engine needs room for 1 full-length request; 97 fit). If generation turns out slow because of preemption, `vllm_gpu_memory_utilization` 0.24 (+3.8 GiB, +21 %) is the knob
(it needs 0.24 x 95 GiB free at the start, which holds when the trainer is restarted; the other 13 GB on the card belongs to another job).

**Trainer micro-batches.** `mb = min(micro_batch_seqs, micro_batch_tokens // longest sequence of the step)`. The supervisor starts at rung 0 (`24576 128`, as in every RL phase so far,
no OOM in any of them: `rl_sup` / `rl2_sup` / `rl2b_sup` / `rl2c_sup` logs). At b2048 the longest sequence is ~9.3k tokens -> **2 sequences per micro-batch** (18.6k <= 24.6k tokens: the
same activation volume as b1024 at 5 sequences), 168 micro-batches per update (+ the reference forwards) instead of 134. Logits are chunked (`loss_chunk_tokens` 2048 -> 2.1 GB fp32), the
sdpa masks are [mb, 1, L, L] booleans (2 x 87 MB per mask type at L = 9.3k).
The ladder `24576 / 12288 / 6144 / 3072` **collapses**: the last three rungs all give 1 sequence (9.3k tokens) because the budget is below one sequence; if a single 9.3k-token
sequence OOMs the supervisor cannot help and gives up after 8 starts in an hour (`RENTAL_RL2C_GAVE_UP`). Unknown that decides it: whether PyTorch sdpa runs a memory-efficient (O(L))
kernel for Gemma-3's boolean mask at head_dim 256 on this card. Evidence for yes: the b1024 stage of phase 2 (L up to 4.9k, 5 sequences) and every stage so far ran without OOM at
a 45 GB trainer; a math fallback would need ~34 GB for the attention matrices of b1024 alone. `scripts/probe_microbatch_memory.py` measures this on a free GPU
(`--lengths 4900x5 9300x2 9300x1`); I did **not** run it (the GPU is busy: 76 GB used, three processes). Fallbacks if it OOMs at 1 sequence: override `gradient_checkpointing=true`
(slower, ~1.3x update time), or `max_new_tokens_by_bin.b2048=6144`.

## 9. Risks and open points

1. **Re-derived filters** (section 2): four exact, three approximate; the b2048 windows are comparable to, not identical with, the b1024 distribution (Flesch / repetition identical, artifacts
   slightly different). 24 % of the rows are wikipedia (share-alike) as in the other bins; licence column present for per-licence filtering.
2. **9.3k-token micro-batches** (section 7): untested on the GPU; ladder collapse.
3. **Time**: ~17 h for 100k completions on a quiet host, +30-80 % with the present CPU contention; the mixed stage doubles.
