# Vocabulary-pruning ablation (VA report, saved 2026-10-25)

Model: final run (final2-step401), Q8_0 GGUF, llama.cpp CPU, RTX 3060 box (Xeon E5-2697A v4, AVX2). Rule written before running (`translate_pipeline/vocab_ablation/DECISION_RULE.txt`): adopt head pruning if CPU speed >= 1.3x with paired chrF++ loss <= 0.2; full pruning also needs the file <= 50% and no new copy failures. Results and scripts: `translate_pipeline/vocab_ablation/results/` (DECISION.md, csv/), private Hub repo `<HF_ORG_LEGACY>/sabiyarn-vocab-ablation-2026-10-25` (98 files).

DECISION: keep A0 (full vocabulary). Pruning is lossless but does not buy enough.

- Allowed sets from the tokenizer alone (no corpus): Latin set 158,767 of 262,144 tokens (60.6%: specials, byte tokens, ASCII, Latin letters incl. African orthographies and combining marks, punctuation, symbols, whitespace pieces); Latin + 862 Ethiopic tokens = 159,629 for amh/tir. One lite vocabulary covers all 77 target languages (75 Latin, 2 Ethiopic). Reference-token coverage 100.000% in all six measured languages (swh, hau, yor, kin, amh, tir); the other 71 languages have no references on the box (coverage 100% by construction for Latin text). The set cannot shrink much by script: 145,668 tokens are pure ASCII. Sets built from small target-language train text cover only 98.1-98.3% (fail the 99.5% gate); trimming by token id does not work (60k tokens cover about 55%).
- A3s (fully pruned, llama.cpp): file 225.1 MB (75.1% of 299.7 MB), RSS 486 vs 596 MB, speed 2.219 vs 1.654 sentences/s = 1.235x (paired ratios 1.228, 1.350 (contaminated), 1.235; clean repeat 1.245, 1.236, 1.231), chrF++ 34.886 -> 34.901 (loss -0.015 [-0.045, 0.000]), finished 100%, wrong-language 0%, 99.91% identical text (1,169 of 1,170 sentences token-identical), preservation test (240 English items with names, numbers, URLs, code, LaTeX, emails) identical (A0 itself passes only 60.4%), re-spelling of pruned source tokens 0 of 52,132 on test sources (1 of 14,820 on Wikipedia-simple sentences).
- A1 (logit mask) and A2 (sliced head) are token-identical to full-vocabulary decoding. A2 cannot be loaded by llama.cpp (`output.weight has wrong shape`: would need a patch); in PyTorch CPU it gives 1.204x at 159.6k tokens. On GPU (torch, batch 64) the sliced head is about 1.0x (head is 2% of the step).
- Where the time goes: llama-bench single sequence, 4 threads: head about 55% of decode time (5.95 of 10.9 ms); speed-up vs full vocabulary 1.28x at 159.6k, 1.44x at 120k, 1.64x at 80k, 1.87x at 40k tokens (speed-only proxy models). In the full server at batch 8 only part of the step depends on the vocabulary, so the end-to-end gain at 159.6k is 1.235x. Reaching 1.3x needs K <= 120k tokens with >= 99.5% coverage, which needs frequency data from large train-side target text (not done).
- Not run: llama.cpp patch for a split head; per-language trained-set variants; batch-32 and paragraph speed; coverage for the other 71 languages; the 200 real units.
- Practical consequence: the Q8_0 GGUF stays the CPU model. The pruned lite GGUF (225 MB, 23.5% faster, lossless on the tested languages) can be rebuilt in about 40 s (`va_prune.py prune`) if a smaller file matters (client snippet in `scripts/client_lite.py`: token-id prompts mapped through `keep_lite.npy`).
