# Decisions

Every design decision, with the reason. IDs are stable; open questions are at the end with the DEFAULT this module
adopted until the owner answers. "Repo" = the SabiYarn research repository this module was split from; code was
copied or ported from it, never imported.

## Scope and environment

**D-01 Model and task.** Text-only `Gemma3ForCausalLM` (`google/gemma-3-270m-it`), English source only, African
target only. The loader refuses anything that is not a text-only Gemma 3 causal LM. Target transformers: `>=4.53,<5`
(developed against 4.57.6). 4.53 is where `masking_utils` builds the Gemma 3 global and sliding-window masks per
layer type and accepts them as a dict; `<5` because `unbabel-comet` pins it. torch `>=2.6`: transformers only
derives packed-sequence masks from `position_ids` on torch >= 2.6.

## Format

**D-02 Language table and names.** One table (`gemma_mt/languages.py`): tag, ONE display name, AfriCOMET code,
GlotLID labels, FLORES+/NTREX/MAFAND codes. Names are the short ones the owner uses, never changed after a model
was trained (the name is part of the prompt): Yoruba, Hausa, Igbo, **Pidgin**, Efik, Twi, Ewe, Fon, Wolof, Swahili,
Kinyarwanda, Somali, Oromo, Amharic, Tigrinya, Luganda, Lingala, Zulu, Xhosa, Afrikaans, Shona, Chichewa, Sesotho,
Setswana, Malagasy, Ibibio, Urhobo. Tag for Tigrinya is `tir` (`ti` is an accepted alias); Swahili is `swh`
(`swa`, `sw` accepted when READING data). Aliases are normalised before anything is written, so the model only ever
sees canonical tags. `SUPPORTED_RL` = data languages with a repo-verified AfriCOMET code (20 languages);
Ibibio and Urhobo are explicitly `unsupported`, amh/tir/lug/lin/mlg are `unverified` (see Q-05).

**D-03 The prompt is literal.** `INSTRUCTION_TEMPLATE = "Translate the text to {african_language}:  {english_text}"`
with two spaces after the colon, as the owner types it. It is a constant and tests pin it; do not "tidy" it.
The English text is `.strip()`ped before insertion (the Gemma template `| trim`s the message ends anyway; stripping
first makes the result independent of that filter). Interior whitespace and newlines are preserved.

**D-04 Rendering and tokenization.**
* Rendering always goes through `tokenizer.apply_chat_template`. `format.reference_render` is a re-statement of
  the Gemma 3 template used (a) as the stub tokenizer's template and (b) by `assert_template_matches_reference`,
  which fails fast at the start of data preparation, SFT, RL and evaluation if the loaded tokenizer renders anything
  else (e.g. a different role name or an injected system prompt).
* The rendered string already contains `<bos>`: it is tokenized with `add_special_tokens=False`; a check refuses a
  double BOS.
* Prompt and target are tokenized as two separate segments and concatenated. At inference the model continues after
  the tokenized prompt, so this is exactly what it sees; joint tokenization could in principle merge across the
  `model\n` / tag boundary. `format.check_segment_consistency` compares both on probes with a real tokenizer (the
  gated integration test asserts they agree).
* The trailing `\n` that the template emits after `<end_of_turn>` is kept in the sample (so the string equals the
  template output exactly) and carries label -100.

**D-05 End token.** The owner wrote `{eos_token}`. For Gemma 3 IT the tokenizer's `eos_token` is `<eos>` (id 1), but
the chat turn is closed by `<end_of_turn>` (id 106), and `generation_config.eos_token_id` of the IT checkpoints lists
both. The training target ends with `<end_of_turn>`; `resolve_stop_tokens` verifies at run time that it exists, and
`ensure_generation_config` makes every saved checkpoint stop on `[106, 1]`. `push_model` refuses a checkpoint whose
`generation_config.json` lacks 106.

**D-06 Loss mask.** Loss only on `{iso} {translation}<end_of_turn>`: the iso tag is trained (the model must learn to
emit it), the prompt and the template newline are not. Labels use the HF alignment (same as `input_ids`; the loss
shifts by one). A sample's first token (`<bos>`) is never a target, so the shift never crosses a pack boundary.

**D-07 Prefix handling in outputs.** `strip_iso_prefix` returns `ok | wrong | missing | empty`. Policy flag
`require | forbid | optional`. Evaluation scores the text with the tag stripped when present and the whole output when
absent (so the untrained base model is scored on what it says); the tag status is reported separately as
`prefix_ok_rate`.

## Data

**D-08 Packing.** Best-fit-decreasing over shuffled buffers of 100k samples (O(n log n), tested for completeness,
capacity and efficiency; ~0.99 on realistic length mixes). A sample is never split and never truncated: samples
longer than `max_sample_tokens` (default = seq_len = 2048) are dropped and counted, because a truncated target
would teach the model to stop mid-sentence. Tokens are stored as `uint32` (vocab 262,144), samples back to back with
no stored padding; the loader pads to `seq_len` (or not, for the padding-free path). Resume and sampling order are
pure functions of `(seed, step)`.

**D-09 Splits and hygiene.** Validation is a hash of the split key (default: the English text), 1% by default, so one
English sentence is never in both splits regardless of language or row order. `min_val_per_language` force-adds the
lowest-hash keys of rare languages (only for languages with >= 200 rows) so per-language validation loss exists.
Exact duplicates `(iso, english, target)` are dropped (in-memory hash set: fine to ~20M rows; use an external
dedupe above that). Unknown language tags are dropped and counted, never guessed.

## Attention (cross-sample masking)

**D-10 Mechanism.** Verified numerically on a tiny random Gemma3 (6 layers = 5 sliding + 1 global, window 8,
samples 14-31 tokens): packed logits, summed loss and embedding gradients equal the separate runs to < 1e-5 for
eager and SDPA, with explicit masks and with `position_ids`-derived masks; the unmasked and "positions reset but
causal mask" negative controls differ by ~0.7 in logits.
* **explicit** (default for sdpa/eager): we build `{"full_attention", "sliding_attention"}` 4D masks (bool for
  sdpa, additive for eager) from `segment_ids` and pass the dict as `attention_mask`; works regardless of
  transformers' own packing detection.
* **position_ids**: `attention_mask=None` + restarting `position_ids`; transformers derives the boundaries
  (`find_packed_sequence_indices`) and ANDs them into BOTH layer masks. **Trap found by experiment:** with
  `use_cache=True` (the default in eval mode) the detection is silently skipped (errors ~0.8). `attention.model_inputs`
  always passes `use_cache=False`; a test pins this.
* **flash**: `flash_attention_2` + batch flattened to `[1, N]` + explicit `cu_seq_lens_q/k`, `max_length_q/k`.
  `_is_packed_sequence` only fires for batch size 1, so a padded `[B, T]` batch would be silently contaminated;
  the collator's `flatten` mode removes padding entirely. The sliding window is per-sequence inside the varlen
  kernel. NOT executable on the laptop: only the kwargs are tested (against transformers' own helper and the
  signature of `_flash_attention_forward`); the real equivalence test is in the gated integration tests.
* Why SDPA is the default and not `eager`: Gemma 2's reasons for eager (attention logit soft-capping) do not apply to
  Gemma 3 (QK-norm instead; `attn_logit_softcapping=None`).
* Padding tail of a pack is its own segment (positions 0..k-1, segment 0, label -100), so no row is ever fully
  masked (no NaN) and no padding token continues a sample's positions.

## SFT

**D-11 Loss normalisation.** `L = sum of -log p over all labelled tokens of the whole optimizer step / number of
labelled tokens of that step`, computed over all micro-batches and (DDP) all ranks; DDP's gradient averaging is
undone by multiplying each rank's sum by `world / N_global`. A mean of micro-batch means is wrong because packed
micro-batches have different target counts; a test shows the two differ and that the trainer's rule equals one big
batch exactly. Consequence: `micro_batch_size x grad_accum_steps` can be traded freely without changing the update.

**D-12 Memory.** 262,144-row LM head: logits for 16k tokens in fp32 would be 17 GB. The loss is computed only at
labelled positions, 512 tokens at a time, each chunk under activation checkpointing (`losses.py`). Equal to HF's
loss (tested), any chunk size gives the same value and gradient.

**D-13 Precision/optimizer.** fp32 master weights + bf16 autocast (a pure-bf16 update loses small LR steps; fp16
overflows on Gemma 3). Fused AdamW on CUDA, betas (0.9, 0.95), eps 1e-8, weight decay 0.01 on matrices only (not on
norms nor the tied embedding/LM head), grad clip 1.0, linear warmup (3% of steps) then cosine to 10% of peak.

**D-14 Hyper-parameters for a 270M model (starting point; see Q-06).**
* `learning_rate 5e-5`: full fine-tuning of a small model tolerates 3e-5..1e-4; 5e-5 is the middle of the range
  and a common default for full fine-tuning of sub-billion models (not tuned here, see Q-06). The task is narrow, forgetting of general
  chat ability is irrelevant, but too high a rate erases the multilingual knowledge the pretrained embeddings carry.
  Suggested sweep on 10% of the data: {3e-5, 5e-5, 1e-4}.
* batch `131,072` tokens (~2k pairs; 64 packs x 2048): large enough for a stable gradient over 20+ languages, small
  enough to give > 2k optimizer steps on a few million pairs.
* `epochs 3` with early stopping (`patience 5` evaluations, `min_epochs 1`, `eval_every 200` steps): translation
  SFT overfits after 2-4 epochs on small-language data; the best-validation checkpoint (`best/`) is what RL and
  evaluation use.
* `seq_len 2048`: sentence pairs are short; the 270M model's sliding window is 512, packing many pairs per row
  costs nothing because the mask is block-diagonal.

**D-15 Resume and determinism.** `last/trainer_state.pt` holds model, optimizer, step, RNG states and the early
stopper state; the data order is a function of `(seed, step)`. A test runs 6 steps straight vs 3 + resume + 3 and
requires bitwise equal parameters. The state file duplicates the weights (1.1 GB) on purpose: one atomic file.

## RL

**D-16 Algorithm (GRPO, ported from the repo's `rl/policy_gradient.py`, written for HF Gemma 3).**
* G=8 samples per prompt (`group_size`), 16 prompts per step. Sampling at temperature 1, `top_p=1`, `top_k=0`:
  the sampled distribution then IS the scored distribution, so the policy-gradient estimator is unbiased; any
  truncation requires `allow_truncated_sampling: true` and is documented as biased.
* Advantage `A = (r - mean_group) / (std_group + 1e-4)` (the repo's choice: `advantage_norm: mean_std`); a group
  whose std is < 1e-6 gets A = 0. `mean` (no std) is available. The per-language QE reliability weight multiplies A.
* One update per sampled batch by default: exactly on-policy, ratio == 1 (asserted every step; recomputed log-probs
  equal the sampler's to ~1e-5 in fp32, tested), no clipping needed. `num_updates_per_batch > 1` requires `clip_eps`
  (PPO-style clipped surrogate is implemented and tested).
* Loss normalised by the number of completion tokens of the whole step (`token`), or per-sequence (`sequence`).
* KL to the frozen SFT checkpoint, `kl_coef 0.05`. `k3 = exp(d) - d - 1`, `d = log ref - log pi`, as in GRPO and the
  repo. **Documented subtlety (tested exactly on a 5-token vocabulary):** k3's VALUE is an unbiased estimate of
  KL(pi||ref), but differentiating it with samples held fixed gives the gradient of KL(ref||pi). `k2 = d^2/2` has the
  reverse-KL gradient. Default stays k3 (matches the repo and DeepSeekMath); `kl_estimator: k2` is one flag away.
* In-loop assertions (raise, not warn): sequence/score/advantage lengths, finite rewards and log-probs, reward inside
  the configured range, completion-mask counts, log-probs exactly 0 outside the mask, ratio == 1, KL ~ 0 at step 0.
* Single GPU (D-19).

**D-17 Reward (`rl/reward.py`, `rl/reward_shaping.py`, ported from the repo's `rl/shaping.py`, `rl/rewards.py`
and `rlhf/scripts/calibrate_shaping.py`).**
* Sanitisation first (the owner's anti-hacking rule): cut the token ids at the FIRST stop id, decode with specials
  removed, remove any special-token STRINGS typed out as text, strip the leading tag. The scorer only ever sees
  the translation. Nothing after the first `<end_of_turn>` exists for the TEXT the scorer sees (amended 2026-10-17 by D-26: tokens
  after it are now counted and penalised, the text is still cut there).
* Failure classes, each scored with the penalty = floor of the shaped range (default -2.0), never sent to the
  scorer: no `<end_of_turn>` within `max_new_tokens`; missing/wrong tag (policy `require`); empty; copy of the
  source (normalised equality or word-set Jaccard >= 0.9); degenerate repetition (a word repeated > 4 times in a
  row, < 30% distinct words, or absurd compressibility); length ratio outside [0.2, 5]; optional GlotLID mismatch
  (off by default, only for languages with labels and texts >= 15 chars). A penalty above the floor is refused.
* Content = AfriCOMET-QE `masakhane/africomet-qe-stl-1.1` on (English source, translation), in-process fp16,
  batches <= 32, sorted by length and un-sorted (tested), or the same model behind a subprocess worker.
* Shaping: piecewise-linear, monotone, per language. Anchors t_fail/t_mid/t_great = P10/P50/P90 of QE on human
  references of that language (t_fail further raised to the P90 of QE on mismatched references and never below
  0.46); `calibrate_shaping.py` measures them on the FLORES+ dev split and also reports AUC against mismatched, copied
  and half-omitted translations; a language with AUC < 0.7 is `usable: false` and gets advantage weight 0, otherwise
  the weight is linear in AUC (0.65 -> 0, 0.90 -> 1). Uncalibrated languages use the repo's default anchors
  (0.46, 0.60, 0.75) with a warning. `adaptive` mode (rolling quantiles of the policy's own scores) is ported.
* **Presets: `repo` (default) range [-2, +2.25]; `owner_note` range [-2, +1]** (same anchors, flat above t_mid).
  See Q-01.
* AfriCOMET limits: source and translation are encoded separately and each truncated at 510 encoder tokens
  (read from comet 2.2.7). Prompts are filtered to `src_afr_tokens <= 256`; `max_new_tokens 256` keeps the
  translation inside the limit in practice; `reward/comet_mt_truncated_rate` is logged so a violation is visible.
* The AfriCOMET code mapping, GlotLID label sets and anchors defaults were copied; `auc` now averages tied ranks
  (the repo's version did not), which only matters for heavily tied scores.

**D-18 RL data.** Parquet/jsonl with `english, iso, language, src_afr_tokens, source_dataset`; no reference is
read. Rows outside `SUPPORTED_RL`, with an empty source or `src_afr_tokens > 256` are dropped and counted. The
prompt schedule is stateless in the step number (resume exact): language drawn with probability proportional to
`n_lang ** language_alpha` (1 = natural mix, 0 = uniform), then a prompt uniformly. Evaluation prompts are a
hash-selected hold-out (or a separate file).

**D-19 Single-GPU RL.** The reference model, the scorer and sampling all sit next to the policy; multi-GPU RL
needs per-rank scorers and gathered advantages and was judged not worth the risk for a 270M model. `WORLD_SIZE>1`
raises.

## Evaluation and publishing

**D-20 Evaluation.** One normalised schema `english, reference, iso, benchmark, id` for FLORES+, NTREX-128 and
MAFAND-MT (English-source pairs only), loaded from local files or the Hub, per-language codes in the language
table. Greedy decoding (no sampling, no beams), batched in length-sorted order (tested: batch size does not change
output). Metrics per benchmark and language: chrF++ (sacrebleu, word_order 2), spBLEU (tokenizer `flores200`; falls
back to `13a` offline and says so in `results.json`), BLEU, AfriCOMET-STL-1.1 (with reference) and QE (only for
`SUPPORTED_RL` languages). Macro averages are unweighted over languages. The report puts all systems on the
languages they have in common, shows deltas against a reference system and takes published numbers as CSV.
Only the 270M model is trained; other models are evaluated baselines (`--predictions` scores external outputs).

**D-21 Hub and licences.** Model cards: `license: gemma` plus the Gemma Terms of Use note (derivatives must keep
the terms). Dataset cards: `cc-by-4.0` (changed 2026-10-12 from cc-by-sa-4.0, see Q-13) plus a per-row `licence` /
`source_dataset`. The module's own code is AGPL-3.0-or-later (SPDX header in every file; `LICENSE` holds the notice
and a TODO to add the full text because it was written offline). No file claims that a licence can force third
parties to release data produced with the model. Model cards add `OUTPUT_DATA_TERMS`: a contract offer under which
anyone who publishes or shares a dataset generated with the model grants the publisher a perpetual licence to train
on it, closed models included (Q-13). Push scripts do nothing on import, refuse without `--yes`, default to private repositories under
`<HF_ORG_LEGACY>`, read `HF_TOKEN` from the environment, never upload trainer state, and refuse a checkpoint
without `<end_of_turn>` in its generation config.

## Testing

**D-22 Offline strategy.** The laptop has no GPU, no pytest and only numpy on the default Python; the research
repo's `.venv-comet` has torch/transformers/sacrebleu/comet, used read-only. Tests use pytest syntax; `tests/run_tests.py`
runs them without pytest (a ~100-line shim). Torch tests skip with a reason where torch is absent; the numpy-only
tests (format, packing, data pipeline, masks, reward, shaping, RL data) run on any Python 3.10+.

## OPEN QUESTIONS (the module adopted the DEFAULT shown; tell me to change any)

**Q-01 Which reward range to train with? RESOLVED 2026-10-12 by the owner: `repo`.** The repo's `rl/shaping.py`
maps QE to **-2 .. +2.25** (failure -2..0 below t_fail, 0..+1 to t_mid = human-median anchor, +1..+2 to t_great =
P90 anchor, flat above). The owner first remembered "-2 .. +1", then chose the repo curve ("i believe it is
better"). The anchors stay per language (the AfriCOMET score depends on the language, calibrated with
`calibrate_shaping`). `reward.preset: owner_note` (cap +1 above t_mid) stays implemented but is not used.

**Q-02 GPU.** Is the rented card Ampere or newer (bf16)? Default: yes. If it is a Turing card (2080 Ti) bf16 is
slow/unsupported and the config needs `autocast_dtype: none` (fp32, slower) - fp16 is NOT an option for Gemma 3.

**Q-03 Sample length.** Are all pairs sentence-level (<= 2048 tokens)? Default: yes; longer samples are dropped and
counted in `meta.json` (`dropped.too_long`). If paragraphs/documents matter, raise `seq_len` and re-check memory.

**Q-04 Advantage normalisation.** `mean_std` (repo) vs `mean` (Dr. GRPO argues std-scaling reweights groups by
difficulty). Default: `mean_std`, with a flat-group threshold so noise is not amplified.

**Q-05 AfriCOMET coverage of amh, tir, lug, lin, mlg.** They are not in the repo's `AFRICOMET_SUPPORTED`, so they
are SFT targets but excluded from RL and from AfriCOMET evaluation. If the AfriCOMET model card confirms them, move
them to `VERIFIED` in `languages.py` (one line each, plus GlotLID labels); `calibrate_shaping` will then decide per
language whether QE is usable.

**Q-06 SFT hyper-parameters.** lr 5e-5, 131k tokens/step, 3 epochs, patience 5 are reasoned defaults, not tuned.
Default plan: a 3-point lr sweep on 10% of the data before the full run.

**Q-07 Benchmark language codes.** FLORES+ codes follow FLORES-200 (`gaz_Latn` for Oromo, `plt_Latn` for Malagasy);
NTREX-128 and MAFAND-MT codes are ISO-639-3 with `swa`. They could not be verified offline (MAFAND's `en-*` configs
were read from the locally cached loading script; the others from memory). `python -m gemma_mt.eval.benchmarks
--benchmark X --path P` prints what is actually found; absent languages are reported as no data, never filled.

**Q-08 Licensing review.** Some source datasets in the research repo are non-commercial (e.g. CC-BY-NC). A Gemma
derivative trained on NC data may not be releasable as `license: gemma` without restriction; the dataset card says
cc-by-4.0. Default: all repositories private; someone with legal responsibility should review before `--public`.
The Gemma Terms of Use also require passing the terms on; the card text is a note, not legal advice.

**Q-09 Vocabulary.** 168M of the 270M parameters are the 262k-row embedding. Pruning it to the tokens that occur in
the target languages would speed training and shrink the model but changes the tokenizer. Default: not done.

**Q-10 GlotLID guard.** Off by default (needs `fasttext` + download; GlotLID is unreliable on short texts and for
Pidgin/Fon/Efik). Default: off; the tag check + QE + copy guard are the protection.

**Q-11 Reference-based RL reward.** The reward is reference-free by the owner's instruction (RL prompts carry no
reference). If references exist for part of the data, a blend with AfriCOMET-STL or chrF++ (the repo's
`chrf_anchor`) would reduce reward hacking; not implemented. Default: QE only.

**Q-12 Experiment tracking.** wandb is optional (`wandb_project`); jsonl logs are always written. Default: jsonl only.

**Q-13 Licensing goal (owner, 2026-10-12): keep our models private, but be free to train on data other people generate
with the fine-tuned Gemma, without any obligation to open-source.** This replaces the earlier goal of making others'
data open. Consequences implemented: (1) our datasets are `cc-by-4.0` (attribution only; no share-alike, so using
them in a closed model is allowed; the owner also allowed CC-BY-4.0 sources for the same reason); (2) the model cards
carry `OUTPUT_DATA_TERMS`, a grant-to-publisher for datasets that someone publishes or shares after generating them
with the model; nothing obliges anyone to open their models; (3) the code stays AGPL-3.0-or-later for now - the
owner is the copyright holder, so AGPL does not bind them, but it would discourage others from reusing the module;
Apache-2.0 would be the consistent choice if wide adoption is wanted (not changed without asking).
Limits, stated plainly: the grant is a contract term, so it binds only people who accept it (a *gated* model repo
makes acceptance explicit; an ungated card is weak evidence), it cannot reach people who generate data and never
share it, and Gemma's Terms of Use still apply to anything trained on Gemma outputs (a model trained on generated
data is a Gemma "Model Derivative": use restrictions pass through when it is distributed; private use needs
nothing). Sources with a share-alike licence (CC-BY-SA, ODbL) would force share-alike on the dataset: the pairs
carry a `licence` column so those rows can be kept out of the cc-by-4.0 push. Needs a legal read before `--public`.

**D-22 Reverse direction (owner 2026-10-12: "add backward translation", meaning African -> English).** One model, one
format: the instruction is the SAME template with `English` as the target language and the answer starts with the pivot
tag `eng` (`languages.PIVOT_ISO`, deliberately not a row of the language table: no language id, no RL slot, no
benchmark code). Why the same template: the owner's fixed English->X template needs no second form, the model learns
"the language after `to` is the output language", and the stop/prefix handling (`strip_iso_prefix`) is unchanged.
The source language is not named (the text identifies it; as in the en->X direction the target is the only control).
Every pair yields both samples (optionally `--x2en-fraction`); both samples share the split decision of the pair, so
a validation sentence is never trained on in the other direction. The `iso_id` stays the AFRICAN language of the pair,
`direction.npy` carries the direction; validation reports en2x and x2en separately. Cost: about 2x the tokens per epoch;
the reverse samples do not need new data or a new QE pass (the pair score is symmetric for our purposes: it was
computed with the English source and the African hypothesis). RL is not changed. Risks: capacity is shared (270M),
low-resource languages may lose a little en->X quality to the reverse samples - check `val_loss_en2x` against an
en2x-only run on a small budget if that matters; X->en evaluation with AfriCOMET is less documented than en->X, so
chrF++/spBLEU are the primary numbers for that direction.

**D-23 Length-staged prompts and chunked (sentence-level) reward (owner 2026-10-12).**
*Inputs.* Prompt sets are balanced uniformly across length bins per language, named by their upper bound in AfriCOMET tokens
of the source: b64, b256, b512, b1024 (Gemma) and b2048 added for SabiYarn. 120k prompts per language for Gemma (30k per bin).
The source is plain running text: NO newline convention (the model must not learn to translate correctly only when a line break
follows every sentence). `length_bin` is a column of the prompt files; `rl/data.py` derives it from `src_afr_tokens` if absent.
*Curriculum.* Training is staged b64 -> b256 -> b512 -> b1024 (`curriculum_steps`: steps per stage, a step draws only its stage's
bin), then a random mixture of all bins ("mixed": the bin of every prompt drawn uniformly). Per-bin prompts per step,
`max_new_tokens` and a token budget for the scoring forward keep the long stages within memory. Stage lengths are fixed step
counts; extend a stage by hand if `finished_rate` or `fail/*` in the log is still bad at its end.
*Reward.* The window is split into sentences at `.`/`?`/`!`/`።` (rl/segments.py: decimals, abbreviations, initials and list
numbers do not split; a newline is just a space). Equal sentence counts: the i-th source sentence is scored against the i-th
output sentence. Different counts: Gale-Church length alignment (merged and split sentences become many-to-one beads, an
omitted source sentence a failed chunk with the penalty; a single-sentence output is scored as a whole). Every scored chunk
is at most 510 AfriCOMET tokens, so the 512 limit of the encoder does not bound the document. Chunk rewards are shaped per
language and averaged WEIGHTED by source characters (`reward.chunk_agg: source_length`; `mean` = plain average). Copied or
empty chunks get the failure score. Whole-text scoring (`chunking: off`) is still available and unchanged.
*Not in the RL stage:* the SFT translation data are existing Hub datasets, mostly sentence-level (82% of the pairs are one
sentence). Optional `gemma_windows.py` regroups consecutive pairs of one source into windows of the same bins (pseudo-paragraphs:
the pair files are mostly shuffled); `configs/sft_long.yaml` uses 4,096-token packs for them.

**D-24 Corrected reward for low-reliability languages (owner 2026-10-13, Pidgin).** Measured on MAFAND en-pcm (train 4,790 for fitting, dev
1,484 held out; 8 corruption types built from the SAME source; human reference vs corrupted version, 13,335 validation rows):
raw AfriCOMET-QE same-source accuracy 0.847 mean; 0.943 on length-matched wrong sentences (so wrong content of the right length is already
ranked correctly); 0.47 (chance) when an unrelated fluent sentence is appended; 0.995 on copies. A learned correction (logistic regression on
QE + lengths + GlotLID + repetition) reached 0.957 overall but only 0.945 on the length-matched set: the whole gain is the length term. So the
correction is NOT a re-scaling of the QE number (that cannot change a within-group ranking); it is: (1) text beyond the human length window of
the language is a failed chunk (`extra_output_penalty`, window from the calibration file `len_ratio` p05/p95 widened by `length_slack`, clamped
to [0.3, 2.5]; 1.8x when no calibration), (2) an optional soft penalty per log-unit outside that window (`length_penalty`), (3) the reliability
weight comes from same-source accuracy (`reliability_from: same_source`: mean of mismatch and half-omitted accuracy mapped 0.5 -> 0, 0.9 -> 1)
instead of the cross-sentence AUC that GRPO never uses. For Pidgin this moves the reliability from 0.43 to 0.80. The copy-overlap feature of
the first fit got a positive weight (rewards copying) and was dropped; copies are caught by the existing copy guard. The learned classifier
(gemma_calibration/pcm_calibrator_v1.json) is kept as a reference only, it is not in the reward. Limits: corruptions are synthetic; the real test
is the policy's own outputs (compare reward ranking with MAFAND chrF++ per RL stage); FLORES+ for afr efi ewe fon orm som sot wol is still missing.

**D-25 Lexical-fidelity penalty (owner 2026-10-13: "since Pidgin is similar to English, look at shared stop words / nouns that should not change").**
New `rl/lexical.py`. Per scored chunk four overlap features between the English source and the output: anchor recall / precision (numbers and
mid-sentence capitalised words = names, places) and content-word recall / precision (>= 4 letters, not a stop word). Same MAFAND en-pcm
experiment as D-24 (fit on train, 13,335 held-out validation rows; failure = the corrupted version scores at least as high as the human
reference of the same sentence): raw QE 0.153; QE + length 0.045; + anchors 0.031; + anchors + content words + language id 0.024; on length-matched
wrong sentences 0.057 -> 0.029; mismatched 0.195 -> 0.009, neighbouring sentence 0.311 -> 0.028, appended unrelated text 0.530 -> 0.009. The gain
is almost all on the PRECISION side (output words that do not come from the source); content-word recall got a negative weight (a Pidgin
paraphrase legitimately drops source words) and is not penalised. Copying the source got worse in the learned model (0.005 -> 0.056) because a copy
shares every name and word, so the feature is used as a PENALTY ONLY: deficit = mean over the enabled features of max(0, p10_human - f) / p10_human,
reward -= `lexical_penalty` * deficit, never below the failure floor; the copy guard stays a hard failure class. Features are enabled per language
only where the human references actually carry the overlap (median >= 0.5 for names/numbers, 0.25 for content words; calibration block `lexical`
in the shaping file), so it is effectively on for Pidgin and (names / numbers only) elsewhere. Limits: synthetic corruptions on news text; must be
re-checked against policy samples and MAFAND chrF++ per RL stage.

**D-26 End-of-turn discipline (owner 2026-10-17: "rl should also be penalized for not ending translation firmly with our eos_token and still
outputting rubbish after this eos_token").** The reward now checks four things about how the sampled ids end; every violation is a FAILURE class
(no QE call, reward = the class penalty, default the common floor -2.0 = `-neg_scale`):
(a) `no_end_of_turn` (already a class since D-17, always on): no stop id (`<end_of_turn>` / `<eos>`) inside `max_new_tokens` = TRUNCATED.
(b) `post_eos_rubbish` (new): after the FIRST stop id, any token that is neither padding (`pad_id`, from the tokenizer or the `pad_id` argument of
`TranslationReward`) nor another stop id (`text.decode_completion(..., pad_ids)`; `Sample.post_stop_tokens` carries the count for tokens the sampler
produced and `generate_completions` already cut, `Rollout.post_stop_tokens`): more text, a new turn marker, role names, a repeated answer.
(c) The text sent to QE is only the part before the first stop id (unchanged since D-17: `cut_at_stop`), so even with the check off, rubbish
after the end token can never be scored or earn reward.
(d) `dangling_marker` (new): before the stop id the answer contains a turn / role marker: `<start_of_turn>`, `<end_of_turn>` typed out, `<|assistant|>`,
`<|user|>`, `<|system|>`, `<|im_start|>`, `<|im_end|>` (decoded from the ids WITH specials, `text._TURN_MARKER`), or ends with a bare role line
(`\nmodel`, `\nuser:`, `\nassistant`; `guards.has_role_tail`; exempt when the English source itself ends with such a line; a role word inside a
sentence never matches).
*What can occur with the stock sampler.* `generate_completions` stops HF `generate` on `<end_of_turn>` / `<eos>` and HF pads finished rows with
`pad_token_id`, so (b) is 0 for every row (tested on the tiny model: `post_stop_tokens == [0]*6`) and cannot fire; it is armed for a sampler that keeps
generating after the end token (eos ignored, `min_new_tokens`, vLLM `ignore_eos`, a custom decoder) and for anyone who calls the reward with raw
ids (tests do). The realistic failures with the stock sampler are (a) and (d): a model that never stops, and a model that writes `<end_of_turn>`-less
turn headers (`model`, `<start_of_turn>`) into its answer. Before D-26 a typed `<start_of_turn>` inside the text was silently removed (counted in
`special_stripped_rate`) and the rest scored; now the row fails. `penalize_special_tokens` (all special ids / strings) stays off and independent.
*Config* (`configs/rl.yaml`, `reward.`): `eos_discipline: true` switches (b) and (d) (a stays on); `eos_truncated_penalty`, `eos_post_end_penalty`,
`eos_dangling_penalty` (null = common penalty) set a class value; a value ABOVE the floor raises (a failure may never outscore a translation), a
value below it is allowed and extends `reward_range` (the in-loop range assertion follows). Diagnostics: `RewardOutput.status` has
`post_eos_rubbish` / `dangling_marker`; stats `fail/post_eos_rubbish`, `fail/dangling_marker`.
*Limits.* Only the ids the reward is given can be checked: if the sampler cuts and drops the tail without reporting it, the tail is invisible.
Padding that is also a stop id is indistinguishable from repeated stops and is allowed. Text that repeats the answer BEFORE the end token (a
doubled translation) is not an EOS problem: the length-window rule of D-24 and the repetition guard handle it. The check cannot see what the
model would have written after the end token had the sampler not stopped it, so it does not teach the model to emit padding after the end token
(it is never in the loss; the completion mask ends at the stop id).

**D-27 Chunk semantics shared with the SabiYarn RL reward (2026-10-17).** The planning and aggregation of D-23/D-24 now live in `rl/chunk_plan.py`
(pure functions `plan_chunks`, `aggregate`; `TranslationReward` calls them; outputs verified bit-identical to the previous inline code on 120 random
samples x 6 configurations). The SabiYarn module (`rl/chunking.py` in the research repo, no gemma_mt dependency on its box) carries a file-for-file
port of `segments.py` + `chunk_plan.py` + the copy guard; `tests/test_chunking.py` of the research repo asserts equality on a fuzz corpus. Change both

**D-28 Rollouts with vLLM instead of HF `generate` (owner 2026-10-17).** `sampler: vllm | hf` in `configs/rl.yaml` (default `vllm`; `hf` is the unchanged old path
and the only fallback: a failing engine NEVER falls back silently, it raises `SamplerError` and the run stops). New files: `rl/vllm_engine.py` (engines),
`rl/vllm_sampler.py` (sampler, `HFBackedEngine` CPU stand-in), `scripts/vllm_smoke.py` (GPU test), `tests/test_vllm_sampler.py`; touched: `train_rl.py`
(rollout / eval plumbing, `vllm_*` keys), `eval/eval_translation.py` (`generate_translations(sampler=)`), `scripts/vast_train_rl.sh`. Measurements, commands and risks:
`reports/gemma_rl_vllm_2026-10-17.md`.
*Contract kept.* The sampler returns the same `Rollout` as `generate_completions`: ids exactly as generated (prompts go in as token ids, `skip_tokenizer_init`,
nothing is decoded or re-encoded), cut after the first stop id (`<end_of_turn>`, `<eos>`; passed as vLLM `stop_token_ids`, the stop id is part of the ids),
`finished = a stop id is present`, `post_stop_tokens` computed as before (0 by construction: the engine stops at the stop id, so the D-26 `post_eos_rubbish`
class stays unreachable, as with HF), the same per-bin `max_new_tokens`, temperature 1 / top_p 1 / top_k 0 (the checkpoint's generation_config defaults are
ignored: `generation_config="vllm"`), G = 8 completions per prompt (`n=8`, prompt shared through the prefix cache), seeds per prompt `derive_seeds(seed, step, i)`
(the n children get seed+0..n-1; same step -> identical ids, tested), eval passes (dev chrF++, held-out reward) = temperature 0 on the same engine. The
sampler double-checks the engine's answer (finish_reason vs ids, id count, stop id present, nothing longer than the budget) and raises on any disagreement.
*Log-probs are not needed from the sampler.* `train_rl` recomputes log p(sampled ids) with the current policy by teacher forcing (`losses.completion_logprobs`);
with `num_updates_per_batch: 1` `old_logp` is that value detached (ratio == 1, asserted every step) and the KL uses the frozen reference. vLLM log-probs are used
only as a consistency check: every `vllm_check_every` (25) steps the engine returns log p of its own samples and the run STOPS when the mean |difference| to the
trainer's exceeds `vllm_logp_gap_tol` (0.25; measured bf16 noise ~0.015, a stale / mis-mapped engine is far above). `check_sampler_logprobs` still works for HF.
*On-policy sync.* The engine holds a bf16 copy of the policy (the trainer keeps fp32 master weights, the loss runs under bf16 autocast as before). Before every
rollout / evaluation whose weights changed (version = optimizer steps taken) `VLLMSampler.sync` pushes all parameters (tied embedding once, 236 tensors) with
`model.load_weights` INTO the engine's existing tensors (CUDA graphs stay valid), checks that every engine parameter was written, and resets the prefix cache
(cached KV belongs to the old weights; tested: same prompts after a new sync give the new continuation). `generate` before the first sync raises.
*Two process layouts, same code* (`vllm_mode`). `worker` (default): the engine lives in a child process started with `vllm_python` (the environment that has
vLLM 0.31 / torch 2.13), the trainer keeps its own environment untouched; requests / answers are pickles on a unix socket, weights go through one shared-memory
file on /dev/shm that both processes mmap (GPU -> host once, no serialisation): 0.8-1.1 s per sync. `inprocess`: engine inside the trainer's interpreter
(`VLLM_ENABLE_V1_MULTIPROCESSING=0`), weights GPU -> GPU: 0.03 s per sync; needs ONE environment with vLLM and the project's packages (measured to work in
`venv_vllm` + pandas/pyarrow from a `--target` dir, with identical outputs to worker mode). Worker was chosen as the default for robustness (no
shared-environment constraints, an engine start-up failure leaves the trainer's process clean, the foreign `venv_vllm` stays read-only); the 1 s/step it
costs is below 5 % of any step except b64. Optional `vllm_sleep` (level-2 sleep while the policy trains) works (engine process 4.7 -> 1.5 GiB, wake-up 0.2 s) but is
off: the 270M policy needs no GPU memory relief.
*Limits.* (1) Sampling distribution = vLLM bf16, scoring distribution = trainer fp32-under-autocast: they differ by bf16 noise (mean |dlogp| 0.01-0.02, p99 0.2,
first-token TV 0.02-0.04 on peaked distributions); no importance correction is applied, the in-loop gap check is the guard. (2) The SFT checkpoint is private, the
tests used the base `gemma-3-270m-it` architecture (weights are overwritten by the first sync). (3) Greedy outputs differ from HF in ~half of the sequences after
some tokens (bf16 near-ties); dev chrF++ of the SFT start must therefore be measured with the SAME sampler as the later evaluations (it is: the baseline eval
at step 0 uses the engine). (4) vLLM can start only if `gpu_memory_utilization` x total memory is FREE, even with a fixed KV size; (5) /dev/shm is noexec on the
rentals: the engine's Triton / compile caches must be on disk (`scripts/vast_train_rl.sh` sets them).

**D-30 Omission / extra-sentence detector (owner 2026-10-17, decision 1; finding F2).** A translation that drops a sentence is a failed chunk with the dropped SOURCE characters as weight; a translation with extra sentences gets the existing
`unmatched_output` failed chunk. Why the old planner missed it: Gale-Church used the observed output/source ratio of the very pair (a drop just makes the output "shorter overall") and a Gaussian length cost for the omission bead (an empty output is 4+ sigma
away), so a 2:1 merge always won (2 omission beads in 20,000 synthetic trials; on 8 languages x ~900 real FLORES+ documents 0% of the dropped sentences found, 42% of the appended extra sentences). Design (all new arguments are optional and default off, so the
function is bit-identical to D-27 without them and the SabiYarn port still passes its equality test): `segments.LengthModel` (language ratio and variance from the calibration `len_ratio.corpus` / `.s2`, constant omission / extra bead cost in nats, the two
beads *directional*: omission only when the output has fewer sentences than the source, extra only when it has more), `segments.align_beads` (beads with sentence indices), `chunk_plan.plan_chunks(length_model=, short_frac=0.7, short_min=0.15)` (omission bead -> failed
chunk of the dropped source characters; shortfall check: a merged bead of >= 2 source sentences, or the one-output-sentence "whole" case, whose output is below 0.7 x the expected length and misses >= 15% of the bead's source is split into a scored chunk and a failed
chunk of the missing source characters, total weight unchanged). It only acts when the sentence counts differ; equal counts and single-sentence sources are planned exactly as before (400-sample fuzz against the pre-change package: features off -> identical
rewards / status / qe / weights; detector on -> identical on all 132 single-sentence and 150 equal-count samples). `reward.omission_detector` (yaml true), `omission_cost` (null = per-language `omission.cost` of the calibration, else 4), `omission_short_frac`, `omission_short_min`.
Chosen by measurement (`rl/omission_eval.py`; documents = 3-12 consecutive FLORES+ dev pairs, random tilings, untouched / k random sentences dropped / one sentence kept / 1-2 foreign sentences appended or inserted; macro over yor hau ibo swh zul amh kin ewe):
raised omission/extra priors alone 0% recall (the Gaussian length term dominates); shortfall check alone (legacy alignment) 53% recall / 36% precision / extras unchanged; language-aware DP with constant costs: cost 3 61% recall, 2.6% false alarms; cost 4 56% / 2.1%;
cost 5 51% / 1.6%; non-directional costs add 0.5-0.8% false omission flags on extra-sentence documents; shortfall on top adds only the keep-one case (100% found). Final (cost 4 + shortfall, 8 tilings): sentence recall 56%, precision 64%, documents with >= 1 dropped sentence
found 77%, dropped-character coverage 89%, one-sentence-kept 100%, extra sentences found 93% (appended) / 92% (inserted) against 42% / 40% before, false alarms (an omission-type flag on an UNTOUCHED human document) 0.6% over seven languages and 13.6% for ewe,
macro 2.2% (v1: 0.3%). The target (< 2%) is met in 33 of 40 languages (macro 1.1%; per-language table in `reports/rl_reward_explained_2026-10-17_v2.md` section 4.5); the exceptions are languages whose human translations often change the sentence count (ewe 13.6%: its FLORES+ references
themselves drop sentences; bam 3.4, amh 2.6, fon 2.6, kbp 2.1, luo 2.1, twi 2.1). Per-language operating point (calibration block `omission`, `omission_eval --calibrate-omission`): the smallest omission cost of 4 / 5 / 6 / 8 / 12 with <= 2% false alarms on the
language's untouched dev documents (34 of 40 keep 4; fon, nus 12; kbp 8; kik, lug 6; nya 5; ewe cannot reach it and keeps 4). Not used: sentence-count mismatch plus per-chunk QE (QE only rates a half-translated chunk "mediocre", needs the GPU, cannot say what is missing).
Limits: dev data of one corpus; a "dropped" sentence is a whole sentence (real omissions are often partial: only QE and the length window see those); a drop plus an extra sentence (equal counts) is not detected; the old `appended_text` rule (D-24) still flags 2-10% of faithful
human documents (finding F15). CPU cost 0.4 / 2.3 / 10 ms per 5 / 12 / 30-sentence document (only when counts differ).
