# GPU RAM of the RL stack for the 385M grown model (2026-11-01)

Nothing was run on a GPU. Labels: MEASURED-ELSEWHERE = a number from an earlier report/yaml (270M policy); ESTIMATED = arithmetic from those numbers. Expect +-25 %; the preflight settles it.

Model: 39 layers = 36 sliding (window 512) + 3 global (layers 12, 25, 38; `sliding_window_pattern` 13), hidden 640, 1 KV head, head_dim 256, 385,144,448 parameters
(embedding 167,772,160, rest 217,372,288), vocabulary 262,145 (tied embedding).

## Anchors (MEASURED-ELSEWHERE)
* Final-run shakedown, nvidia-smi per process, 270M policy (18 layers), `micro_batch_tokens` 49,152, RTX PRO 6000 96 GB (reports/final_run_integration_2026-10-21.md): **trainer 42 GB, vLLM 20 GB (0.20 of the card), QE worker 3-7 GB, 65 GB total**; launcher preflight asks 70 GiB free.
* `scorer.batch_size: 128  # the pair (AfriCOMET-QE + SSA-COMET-MTL) peaks at 6.7 GB at 128` (every clean-rerun yaml).
* vLLM engine process 4.7 GiB awake / 1.5 GiB asleep for the 270M model (DECISIONS D-28).
* Logits of 16k tokens over the 262,144-row head in fp32 would be 17 GB; the loss is chunked (`loss_chunk_tokens` 2048), D-12.

## What this changes in the configs
* The clean-rerun ladder starts at `micro_batch_tokens` 49,152 (fits the 270M model). For 39 layers it would OOM at the start; `scripts/launch_clean_rerun_385m.sh` sets `LADDER_START=1` (24,576 tokens, 128 seqs). Total tokens per step are unchanged (accumulation), only the micro-batch is smaller.
* vLLM concurrency: at the same 0.20 budget the KV pool holds about half the tokens of the 270M run (39 vs 18 layers) unless the engine allocates sliding-window layers at 512 tokens. In b64 (512 sequences x ~500 tokens = 256k tokens) the pool is enough on 80/96 GB; in b512/b1024/mixed/final (up to 4.9k tokens per sequence) concurrency drops to roughly 60-80 sequences: slower rollouts, not a failure. If the preflight shows long-bin rollouts are slow, raise `vllm_gpu_memory_utilization` to 0.30 for B2/B3/mixed/final on 96 GB, or check the vLLM version for the hybrid KV allocator.
* Launcher guards: `ALLOW_GPU=1` is needed on any card that is not an RTX PRO 6000; `MIN_FREE_GIB` (70) must be lowered for 48/40 GB cards.

## For the preflight to settle (the 49-step stage)
1. Real peak per process (`nvidia-smi --query-compute-apps` and `torch.cuda.max_memory_allocated`) at the first b64 steps and at the first long-bin steps: does the per-layer activation figure (1.84 GB per 49,152 tokens) hold for 39 layers with sliding attention?
2. Does the installed vLLM load the 39-layer config with explicit `layer_types` + `sliding_window_pattern` 13, and does it use a hybrid (sliding-aware) KV cache?
3. Step time with and without `gradient_checkpointing` on the chosen card.
4. The three CPU models together (GlotLID + fluency + fastText) add about 2.3 GB of host RAM.
